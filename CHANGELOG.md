# Changelog

The kit's version is the first line of `.claude/rules/spec-driven.md` and `version` in `.claude-plugin/plugin.json`; the installer records it in the project's `.claude/spec-driven.install.json`. Update a project with `/setup <project>` from the newer kit folder.

## Private edition aligned with the upstream harness packs 2.6.5 (2026-11-25)

This kit (the owner's private edition, for private projects) jumps from 2.1.0 to 2.6.5: it takes the process, rules, skills, agents, hooks, templates, scripts, installer and tests of the upstream harness packs at 2.6.5, so every entry below, from 2.2.0 on, now applies here too. What only fitted the upstream organisation is left out or made neutral:

- **Removed.** The platform agents of the `operations` pack (pipeline debugging, the build pipeline and deployment map guides, the monitoring, Kubernetes and GitOps agents) and their copies in the test fixtures; the upstream design specs and their research notes, and the benchmark folders and reports. Names of the organisation, its framework packages, repositories, hosting service, servers and people are gone from every text.
- **Made neutral and configurable.** The `operations` pack keeps two generic agents: `sonar-review` reads the server from the new Pack value **Sonar server URL** (next to **Sonar project key**) and `git` describes a GitFlow-style model on any hosting service. The Blazor and shared architecture rules name the extension methods of "the solution's core configuration package" (`AddCoreOpenIdConnect`, `AddCoreHttpServiceClient`, `X-User-*` headers) instead of one organisation's package. `dotnet-stryker` and `dotnet-sonarscanner` are restored from nuget.org or from the feed the project's own `nuget.config` and tool manifest name. The NuGet packaging rule takes its author from `$(Company)`.
- **Kept.** The generic packs `dotnet-shared`, `dotnet-library`, `blazor-server` and `blazor-wasm`, the mutation check, both hooks byte-identical to upstream 2.6.5, and the kit tests (`node --test "tests/*.test.mjs"`); the C# Sonar profile and the architecture source keys the guideline tests read now live in `tests/data/`. References below to `_specs/KitLean/spec.md`, `_specs/Guidelines/spec.md` and `_specs/HarnessPacks/spec.md` point to the upstream design specs, which this edition does not carry.

## 2.6.5 (2026-11-25): mutate changed lines only, page-level outer test

The owner's decision of 2026-11-25 (decision D23), from the benchmark exp17 (Opus) and exp18 (Sonnet): both builds met the quality floor, but the mutation check of 2.6.4 mutated whole changed files, so the builders added off-scope tests of existing code to reach the threshold (exp18: 11 of 12 new view-model tests off-scope, +14 % cost); and both outer integration tests entered through the view model, not the page, so the grid's sort and paging were caught by one bUnit test only. See `_specs/KitLean/spec.md` BR-85 to BR-89 and AC-89 to AC-93.

- **Changed lines only (BR-85).** `scripts/mutation-check.mjs` computes per production file the line ranges the slice added or modified (`git diff -U0` against `--base`; an untracked file counts whole; a listed file without a changed line is not mutated) and gives Stryker.NET one `--mutate` pattern per range with a text span, `File.cs{start..end}`. Stryker.NET's mutate span takes the indices of the first and the last character, not line numbers, so the script turns each line range into its character span. As a safety net it also filters the JSON report: only mutants whose location intersects a changed range count in the score, the printed list and the committed `mutation-<slice>.md`; the others are counted on one line, `outside the slice: n (not scored)`. The evidence lists the lines mutated per file.
- **No off-scope tests (BR-86).** `build-slice` and the testing guideline (T-4, T-13): a survivor outside the slice's changed lines is never a reason to add a test, and tests for existing behaviour are out of scope unless the spec asks for them (R-1 to R-7, pointed to, not repeated).
- **The outer test through the page (BR-87).** The slice's outer integration test enters through the page or component the user uses, rendered on the real Presentation DI container with the real view model and services, only the browser edge, the clock, auth and the backend client faked; never through the view model, so the page's own wiring (grid rows, sort, paging) is under test: the rules' Slices, `build-slice`, the Project settings' Integration test and UI test lines, the testing guideline's order and R-3. The 2.6.4 open point is closed: a stub slice's test is that same Presentation integration test with the stub as the faked backend client, not a separate bUnit test.
- **Models (BR-88).** The README and the Project settings template (line **Models**) recommend Sonnet 5.5 for `build-slice` (exp18: the same quality floor at 3.22 against 5.78 USD on Opus); spec writing and review stay on the stronger model.
- **Unchanged.** `verify.mjs` and `guard.mjs` (pinned at 2.6.4), the classification rule, the threshold, the exit codes.

### Upgrade notes

- Run `/setup <project>` from this kit folder to update `scripts/mutation-check.mjs`, `build-slice`, the rules and the `dotnet-shared` testing guideline.
- A slice in progress runs the check again with the same `--base`: its `mutation-<slice>.md` is rewritten with only the mutants on the slice's changed lines; classifications of those survivors are kept, rows of survivors outside the slice drop out. Tests added under 2.6.4 only to kill survivors in existing code may be deleted when they have no line in the test list (R-1).
- An outer integration test written against the view model is not rewritten by the kit; the next slice that touches the page enters through it. Add the line **Models** to `CLAUDE.md` § Project settings if you want the recommendation recorded.

## 2.6.4 (2026-11-25): mutation check gate, red check removed

The owner's decision of 2026-11-25 (decision D22): a mutation check becomes the slice's proof that its tests can fail. In the owner's benchmark exp16 it gave the best test quality of the series; the owner accepts its added cost. See `_specs/KitLean/spec.md` BR-79 to BR-84 and AC-81 to AC-88.

- **The mutation check (BR-79).** The `dotnet-shared` pack ships `scripts/mutation-check.mjs`, installed into the project's own `scripts/` folder (not `.claude/hooks/`): `node scripts/mutation-check.mjs --slice <name> --base <commit> [--feature <FeatureName>] [--files ...]` takes the production files the slice changed since the base (under `src/`, no tests, generated code, markup-only `.razor` or resource files), runs Stryker.NET (the local tool `dotnet-stryker`, `-t mtp`, once per production project, mutating only those files, with every test project of Pack values **Test projects**), keeps the JSON and HTML report under `artifacts/mutation/<slice>/` (git-ignored), prints `mutation: score s% (killed k, survived v, no coverage n, timeout t)` and each survivor or mutant without coverage as file:line mutator, and exits 1 below Pack values **Mutation threshold** (default 80) or with any mutant without coverage. When `dotnet-stryker` is not in `.config/dotnet-tools.json` or cannot be restored it stops with "dotnet-stryker not available: the package feed must carry it, see README" and exit code 3, never skipping; Stryker.NET failing or writing no report is exit code 4.
- **The committed evidence (BR-80).** The check writes `_specs/<Feature>/mutation-<slice>.md`, committed with the slice: the score line, the files mutated and each survivor with its classification and one line why; a classification written there is kept when the check runs again.
- **The classification rule (BR-81).** `build-slice` runs the check after the slice gate. A survivor is 'equivalent' only if no test could ever observe the change (same output, state and side effects for every input); code that is merely untested or 'out of scope' is not equivalent: add or strengthen a test (seen red first) or list it as 'accepted' for the reviewer to approve. Never weaken code or delete a line to raise the score. `spec-reviewer` checks the committed file and the classifications; T-4 of the testing guideline names the mutation check as the proof.
- **The installer (BR-82).** A pack may hold `scripts/` (into the project's `scripts/`) and pin local .NET tools (`dotnetTools` in `pack.json`): `dotnet-shared` pins `dotnet-stryker` 5.1.0 in `.config/dotnet-tools.json` next to the project's own tools (a tool the project already pins is left at its version, with a note); `remove` takes away only what the kit added. The Project settings template gains the Pack values **Test projects** and **Mutation threshold** (`80`).
- **The red check removed (BR-83).** The mechanical red check of 2.6.1 and 2.6.2 is gone: `verify.mjs` has no `--start`, `--run`, TRX parsing, red record or "red seen for n of n new tests" line (it is the 2.6.0 runner again); `guard.mjs` no longer refuses edits of the state file or of `red-record.json`; the `RegressionGuard` marker and the `--logger trx` requirement are gone. "See each new test fail first" and the efficient-testing rules R-1 to R-7 (pointed to, not repeated) stay.
- **The README (BR-84)** says that Stryker.NET needs the package feed to carry `dotnet-stryker` (or nuget.org reachable) and how to check it.

## 2.6.3 (2026-11-25): efficient testing rules

The owner's go of 2026-11-25 (decision D21): tests that earn their place, at the cheapest level that catches their likely bug, fewest tests that keep every behavior protected. Sources: Google Testing Blog, Khorikov's four pillars, Kent C. Dodds, Microsoft Learn, bUnit docs. See `_specs/KitLean/spec.md` BR-75 to BR-78 and AC-77 to AC-80.

- **One home (BR-75).** The rules R-1 to R-7 (every test earns its place; never write these; one behavior, one level; assert outcomes; the public surface; fewest tests; coverage is not the goal) are in the `dotnet-shared` pack's testing guideline for agents, § Efficient tests, with their sources line.
- **Pointers, no copies (BR-76).** T-6 and T-13 of that guideline, the test conventions and the Blazor WebAssembly architecture's Tests rows point to R-1 to R-7 instead of keeping their own what-not-to-test lists; T-6 no longer allows a call verification beside any outcome (R-4: only at the system boundary, when the call is the behavior).
- **The test list (BR-77).** `build-slice`'s record carries the slice's test list: one line per new test, test name -> AC -> the bug it catches (R-1); a test without its line is deleted. One real integration test per slice stays (the owner's rule).
- **Unchanged (BR-78).** The red check, `verify.mjs` and `guard.mjs` (still pinned at 2.6.2); `build-slice` stays within 45 lines.

### Upgrade notes

- Run `/setup <project>` from this kit folder to update `build-slice` and the `dotnet-shared` and `blazor-wasm` rules.
- A build's record now lists the test list; a slice in progress adds it before its gate.

## 2.6.2 (2026-11-25): red check by full test name, assertion failures only, committed record

A benchmark build with 2.6.1 and two judges found three defects in its mechanical red check (decision D20, the owner's go of 2026-11-25). Data-driven tests were recorded under the runner's display names and could not be matched: one build had to mark a test `RegressionGuard` to pass, a second failed the gate on 2 correct tests. Any failure counted as red, a compile or setup error included. And the record was git-ignored, editable JSON that nobody could check afterwards. See `_specs/KitLean/spec.md` BR-70 to BR-74 and AC-72 to AC-76.

- **Fully qualified names, each data row (BR-70).** `verify.mjs` records each red by its fully qualified test name with its data row (`Ns.Class.Method(value: 1)`, `Ns.Class.Method (1)`, a row's display name as `Ns.Class.Method [one]`), read from the TRX files the run wrote (`dotnet test --logger trx`; `--report-trx` on the Microsoft testing platform), else from the runner's output. The red check matches a new test only by its fully qualified name (the 2.6.1 bare-name and parameters-ignored matches are gone) and accepts a method with inline data rows (`InlineData`, `TestCase`, `DataRow`) when each of its rows was seen failing; rows from a source need one. The gate lists a test with "k of n rows seen red".
- **Assertion failures only (BR-71).** A red counts only when the test ran and failed on an assertion (xUnit, MSTest, NUnit, FluentAssertions, Shouldly, node, Jest, pytest messages): not a build error, a missing type, an exception in setup or in the code, a skipped or an inconclusive test. `--run` says when a run recorded nothing.
- **A committed record (BR-72).** The record moves from `redRecord` in the git-ignored state file to `_specs/<Feature>/red-record.json`, committed with the slice: one `{ "test", "failure" }` line per test, the failure line without absolute paths or machine and user names. `--start <FeatureName>` names the feature (its spec must exist); `--run` without a started slice runs nothing. The slice gate checks the record against the slice's new tests and names the file to commit; the guard refuses an Edit or Write of it.
- **Texts (BR-73).** `build-slice` (still at most 45 lines), the Project settings' red check, `setup` (TRX for .NET test commands, `TestResults/` ignored), the rules' Gates and the README say the same. Everything else of 2.6.1 is unchanged: the slim `build-slice`, the code analysis once per feature in the final review, the leftover clean-ups. Kit tests in `tests/lean.test.mjs` slice 22; both hooks pinned at 2.6.2 (BR-74).

### Upgrade notes

- Start each slice with `--start <FeatureName>` (was `--start`); `--run` refuses to run before it.
- Add `--logger trx` to every .NET test command in `verify.commands` and `verify.testCommands` (`--report-trx` on the Microsoft testing platform), and `TestResults/` to `.gitignore`. Without TRX the record holds display names, which the red check does not match.
- Commit `_specs/<Feature>/red-record.json` with each slice; it is not git-ignored. A `redRecord` left in `.claude/spec-driven.state.json` by 2.6.1 is no longer read: a slice in progress runs its new tests through `--run` once more, or marks them `RegressionGuard` with the reason.
- A stub that throws (`NotImplementedException`) is no red: let it compile and return a default so the test fails on its assertion.

## 2.6.1 (2026-11-24): mechanical red check

The owner's benchmark of 2.6.0 (the benchmark project, CSV slice 1): 11/11 criteria, 10/10 deliberate breaks caught, 0 weak tests, 4.33 USD against 4.29 for 2.5.9; but the build's final answer did not list the failure seen for each test while it was red, although `build-slice` asks for it. A text rule is skipped, so the red check is now mechanical (decision D19). See `_specs/KitLean/spec.md` BR-63 to BR-69 and AC-66 to AC-71.

- **The red record (BR-63).** Every test run made through `verify.mjs` (either gate, and the new `node .claude/hooks/verify.mjs --run "<test command>"`, which runs one of `verify.commands` or of the optional `verify.testCommands`, with any filter) appends each failing test with its first failure line, the command and the time to `redRecord` in the existing git-ignored state file `.claude/spec-driven.state.json`, per working tree. Only `verify.mjs` writes it, from the runner's output; the guard refuses an Edit or Write of the state file. `--start` records HEAD as the slice's start.
- **The red check of the slice gate (BR-64).** Once its commands are green, the slice gate finds the .NET test methods (`[Fact]`, `[Theory]`, `[Test]`, `[TestCase]`, `[TestMethod]`, `[DataTestMethod]`; data rows once per method) added since the slice's start (or the merge base with `verify.baseBranch`, by default `origin/main` or `main`), in changed and untracked `.cs` files, and is red, listing each with its file and line, while one was never seen failing in the red record. A test the slice only modified needs no red. The feature gate is unchanged.
- **The way out (BR-65).** A new test of behavior that already existed carries the marker `// RegressionGuard: <why>` in its attribute block; it needs no red, the gate lists it with its reason, and the build's record and the commit body list it.
- **The green line (BR-66).** A green slice gate ends with `Verification green: <the slice gate>; red seen for n of n new tests.`; `build-slice` starts with `--start`, runs every test through `--run` and quotes that line in its final answer.
- **Code analysis once per feature (BR-67, the owner's correction of 2026-11-24).** As in 2.6.0: the project's **Analysis** (SonarQube) runs once per feature, in the final review, after the feature gate, with the quality gate; never per slice. `build-slice` runs no analysis and its record gives none; the Project settings' Analysis and Fix analysis lines and the rules' Review phase say so.

Kit tests in `tests/lean.test.mjs` slice 21; both hooks pinned at 2.6.1.

## 2.5.9 (2026-11-24): adopted experiment 7, an output and reading diet

The owner's harness experiments of 2026-11-24 adopted experiment 7. On the owner's benchmark the build cost fell from 4.77 to 4.11 USD (-14 %) and the re-read context from 9.5 M to 6.9 M tokens (-27 %), with quality held: 11/11 ACs, gate green, the judge's breaks caught, quality 4/5, a real integration test. Experiment 6 had shown why: cutting the always-loaded instructions by 55 % changed the context only 1 %; the context grows from what the build reads and the output it gets back. After the go `build-slice` writes `_specs/<FeatureName>/slice-<n>-plan.md` from the new `.claude/templates/slice-plan-template.md`, derived from `architecture.md`, with no approval of its own.
- **Outer test first, then red, green, refactor.** The outer test (a new "Outer test" line in Project settings § Test levels; the spec template's "Slice test" column is now "Outer test") is written first and seen failing, then unit test red, change green, refactor, until the outer test is green. A project without the Outer test line uses its Integration test line and says so in the recap.
- **Verified, then the user's check.** A slice ends with `node .claude/hooks/verify.mjs` green and every acceptance criterion in the recap's AC-to-test table, then the recap with its Try-it steps, and stops. The build does not run the human check and never marks a slice accepted: the user checks the slice and accepts it. No deliberate breaks or mutation checks.
- **Commit only when the user asks.** Otherwise the work, the plan and the recap stay uncommitted and the build says so. Batch mode is removed.
- **Final review.** `spec-reviewer` checks the whole feature after the last slice; when a slice is ⚠️, `security-review` runs once with it over the whole diff, never per slice.
- **`slice-verifier` is retired**: removed from the kit, `plugin.json` and every kit text; an update removes the project's unchanged copy. The recap template loses its Verifier and Security review rows.
- `verify.mjs` and `guard.mjs` are unchanged (byte-identical to 2.4.0); the guard's stale `slice-verifier` entry does nothing without the agent. The kit states no turn budget, turn limit or turn counting: limits belong to the job runner.
- Kit tests: `tests/lean.test.mjs` reads the kit's texts per slice, runs the update from 2.1.0 (no `slice-verifier.md`, both new templates), scans for turn budgets, a break marker and `check-slice`, and compares the hooks and the guard tests with 2.4.0.

## 2.4.0 (2026-11-22): the kit runs unattended

Evidence: three Zyggy jobs on a slice of the benchmark project under kit 2.3.0 spent most of their budget on refused tool calls, because the static `ask` rules on `git commit` and `git push` cannot be answered in a job and the verifier's long report filled the session. Every guard rail for an attended developer stays.

- **Commit and push are judged by the guard, not by a static permission rule.** The settings fragment no longer ships `permissions.ask` entries; on update the installer takes away the eight entries an earlier kit added and leaves the project's own rules alone. The guard (`.claude/hooks/guard.mjs`) now answers for `git commit` and `git push`: in an attended session it asks the user, as before; in an unattended job (`ZYGGY_JOB` set, nobody there to answer) it passes them on to the job's own permissions. On a protected branch they are refused in both: the project's list in `.claude/spec-driven.json`, and always `main`, `master`, `dev` and `release/*`. A force-push (`--force`, `-f`, `--force-with-lease`, `+refspec`) and a tag or remote-ref deletion (`git tag -d`, `git push --delete`, `git push <remote> :<ref>`) are refused always. A commit message in a heredoc is not read as a command.
- **The review agents hand back through a file.** `slice-verifier`, `spec-critic` and `spec-reviewer` write their full report to `artifacts/<FeatureName>-slice-<n>-verifier-report.md`, `artifacts/<FeatureName>-critic-report.md` and `artifacts/<FeatureName>-reviewer-report.md`, and answer with one line: the verdict and the path. The guard allows that one write to a review agent on any branch and refuses every other write by the read-only agents; `build-slice` and `write-spec` read the file and carry what matters into the recap or the spec. `artifacts/` is ignored by git (the setup adds it to the project's `.gitignore`) and left out of the verification fingerprint.
- **Test commands with forward slashes.** Every documented test-executable command in the rules, skills, templates and README is written with forward slashes (`src/Test/Unit/X.Tests/bin/Debug/net8.0/X.Tests.exe`), which Git Bash, PowerShell and the jobs all run; the setup writes the project's commands that way, and a kit test refuses a backslash path.
- **The hook sources moved** from the kit's `.claude/hooks/` to `hooks/` in the kit folder; the installer still puts them in the project's `.claude/hooks/`. The copies under the kit's `.claude/hooks/` are no longer read.
- Kit tests: `tests/guard.test.mjs` runs the installed guard on tool calls, attended and as a job; `tests/unattended.test.mjs` covers the settings update, the report channel, the forward-slash rule and the version.
